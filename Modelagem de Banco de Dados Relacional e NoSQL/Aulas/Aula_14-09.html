3. Desenvolvimento Teórico Completo

3.1 Esquemas (Schemas) no SQL Server

3.1.1 O que é um Schema?

Um schema (esquema) é um contêiner lógico que agrupa objetos de banco de dados — tabelas, views, stored procedures, funções, entre outros — dentro de um mesmo banco. Ele funciona como um namespace, permitindo que objetos com o mesmo nome coexistam em schemas diferentes.

Antes do SQL Server 2005, os objetos eram diretamente vinculados ao usuário que os criava. A partir do SQL Server 2005, essa vinculação foi quebrada: o schema é uma entidade independente do usuário, o que permite transferir a propriedade de objetos ou reorganizar permissões sem alterar o código da aplicação[reference:1].

Todo banco de dados SQL Server possui schemas predefinidos:

  • dbo: schema padrão para objetos criados por usuários comuns. Se você criar uma tabela sem especificar o schema, ela irá para dbo.
  • sys: reservado para objetos do sistema. Nunca crie objetos aqui.
  • INFORMATION_SCHEMA: schema padrão ANSI SQL para consulta de metadados.
  • guest: associado ao usuário guest. Em produção, geralmente deve ser desabilitado.
💡 Dica de mercado Em projetos profissionais, evite criar todas as tabelas no schema dbo. Organize-as por domínio de negócio: vendas.Pedidos, estoque.Produtos, financeiro.Faturas. Isso facilita a navegação, a segurança granular e a manutenção[reference:2].

3.1.2 Criando Schemas com T-SQL

A sintaxe básica para criar um schema é:

-- Cria um schema simples
CREATE SCHEMA Vendas;
GO

-- Cria um schema com proprietário específico
CREATE SCHEMA Estoque AUTHORIZATION dbo;
GO

-- Cria um schema e já concede permissão de SELECT a um usuário
CREATE SCHEMA Financeiro AUTHORIZATION dbo;
GO
GRANT SELECT ON SCHEMA::Financeiro TO usuario_consulta;
GO

Após criar o schema, você pode criar objetos dentro dele usando a notação Schema.Objeto:

-- Cria uma tabela dentro do schema Vendas
CREATE TABLE Vendas.Pedidos (
    PedidoID INT PRIMARY KEY,
    DataPedido DATETIME NOT NULL,
    ClienteID INT NOT NULL,
    ValorTotal DECIMAL(10,2) NOT NULL
);
GO

Se você precisar mover um objeto de um schema para outro, use ALTER SCHEMA ... TRANSFER:

-- Move a tabela OldOrders do schema dbo para o schema Vendas
ALTER SCHEMA Vendas TRANSFER dbo.OldOrders;
GO
⚠️ Atenção Ao transferir um objeto entre schemas, as referências em views, stored procedures e código de aplicação não são atualizadas automaticamente. Revise e atualize todas as referências manualmente[reference:3].

3.1.3 Listando Schemas Existentes

Para consultar todos os schemas de um banco:

SELECT 
    name AS NomeSchema,
    schema_id,
    principal_id AS IDProprietario
FROM sys.schemas
ORDER BY name;

3.2 Criação de Esquemas e Tabelas no SQL Server

3.2.1 Tipos de Dados no SQL Server

A escolha correta do tipo de dado é uma das decisões mais importantes no projeto físico. Tipos inadequados podem causar desperdício de armazenamento, degradação de desempenho e até erros de lógica.

Categoria Tipo Uso Recomendado
Numéricos exatos INT, BIGINT, SMALLINT, TINYINT Chaves primárias, contadores, IDs
Numéricos aproximados FLOAT, REAL Cálculos científicos (evitar para valores monetários)
Monetários DECIMAL(p,s), MONEY Valores financeiros (preferir DECIMAL)
Texto VARCHAR(n), NVARCHAR(n), CHAR(n) NVARCHAR para Unicode; VARCHAR para ASCII
Data/Hora DATE, TIME, DATETIME2, DATETIMEOFFSET Preferir DATETIME2 (maior precisão e intervalo)
Binários VARBINARY(MAX), IMAGE (obsoleto) Arquivos, imagens (preferir VARBINARY(MAX))
Especiais UNIQUEIDENTIFIER, XML, JSON (via NVARCHAR) GUIDs, documentos XML, dados JSON
💡 Boa prática Para valores monetários, nunca use FLOAT ou REAL. Esses tipos armazenam aproximações binárias, o que pode gerar erros de centavos em somas e multiplicações. Use DECIMAL(10,2) ou similar.

3.2.2 Criando Tabelas com Restrições

Uma tabela bem projetada inclui restrições que garantem a integridade dos dados:

-- Tabela de Clientes com restrições
CREATE TABLE Vendas.Clientes (
    ClienteID     INT IDENTITY(1,1) PRIMARY KEY,  -- Chave primária com auto-incremento
    Nome          NVARCHAR(150) NOT NULL,
    Email         NVARCHAR(255) NOT NULL UNIQUE,   -- Valor único
    CPF           CHAR(11) NOT NULL UNIQUE,
    DataCadastro  DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
    Ativo         BIT NOT NULL DEFAULT 1,
    LimiteCredito DECIMAL(12,2) NOT NULL DEFAULT 0,
    CONSTRAINT CK_LimitePositivo CHECK (LimiteCredito >= 0)
);
GO

-- Tabela de Pedidos com chave estrangeira
CREATE TABLE Vendas.Pedidos (
    PedidoID    INT IDENTITY(1,1) PRIMARY KEY,
    ClienteID   INT NOT NULL,
    DataPedido  DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
    Status      VARCHAR(20) NOT NULL DEFAULT 'Pendente',
    ValorTotal  DECIMAL(12,2) NOT NULL DEFAULT 0,
    CONSTRAINT FK_Pedidos_Clientes 
        FOREIGN KEY (ClienteID) REFERENCES Vendas.Clientes(ClienteID)
        ON DELETE CASCADE
        ON UPDATE CASCADE,
    CONSTRAINT CK_StatusValido 
        CHECK (Status IN ('Pendente', 'Pago', 'Enviado', 'Entregue', 'Cancelado'))
);
GO

Vamos analisar os principais elementos:

  • IDENTITY(1,1): gera valores automáticos começando em 1, incrementando de 1 em 1.
  • PRIMARY KEY: define a chave primária (implicitamente cria um índice clusterizado).
  • UNIQUE: garante que não haja valores duplicados na coluna.
  • NOT NULL: impede valores nulos.
  • DEFAULT: define um valor padrão quando nenhum é informado.
  • CHECK: valida uma condição lógica.
  • FOREIGN KEY: estabelece relacionamento com outra tabela.
  • ON DELETE CASCADE / ON UPDATE CASCADE: propaga exclusões/atualizações para tabelas filhas.
🚫 Erro comum Usar ON DELETE CASCADE sem analisar o impacto. Se você excluir um cliente, todos os pedidos dele serão excluídos automaticamente. Em sistemas financeiros, isso pode ser catastrófico. Prefira ON DELETE NO ACTION e trate a exclusão logicamente (soft delete).

3.3 Consultas e Operações Avançadas em SQL Server

3.3.1 Common Table Expressions (CTEs)

Uma CTE é uma expressão de tabela temporária nomeada que existe apenas durante a execução de uma única instrução SELECT, INSERT, UPDATE ou DELETE. Ela melhora a legibilidade e a manutenção de consultas complexas, permitindo dividir a lógica em etapas[reference:4].

Sintaxe básica:

WITH NomeDaCTE AS (
    -- Consulta que define a CTE
    SELECT ...
)
SELECT * FROM NomeDaCTE;

Exemplo prático: Vamos calcular o total de vendas por cliente e classificar os clientes por volume de compras.

WITH TotalPorCliente AS (
    SELECT 
        c.ClienteID,
        c.Nome,
        COUNT(p.PedidoID) AS QtdPedidos,
        SUM(p.ValorTotal) AS TotalGasto
    FROM Vendas.Clientes c
    INNER JOIN Vendas.Pedidos p ON c.ClienteID = p.ClienteID
    WHERE p.Status = 'Entregue'
    GROUP BY c.ClienteID, c.Nome
)
SELECT 
    ClienteID,
    Nome,
    QtdPedidos,
    TotalGasto,
    CASE 
        WHEN TotalGasto >= 10000 THEN 'VIP'
        WHEN TotalGasto >= 5000 THEN 'Ouro'
        WHEN TotalGasto >= 1000 THEN 'Prata'
        ELSE 'Bronze'
    END AS Categoria
FROM TotalPorCliente
ORDER BY TotalGasto DESC;

Saída esperada (exemplo):

ClienteIDNomeQtdPedidosTotalGastoCategoria
3Ana Souza1515200.00VIP
1Carlos Lima87200.00Ouro
7Mariana Alves53200.00Prata
🧠 Pare e Pense #1

Pergunta: Qual a diferença entre uma CTE e uma subconsulta (subquery) tradicional? Em que situações uma CTE é preferível?

Reflexão: Uma subconsulta é aninhada dentro de outra consulta, enquanto a CTE é definida separadamente com um nome. A CTE pode ser referenciada múltiplas vezes na mesma consulta, enquanto a subconsulta precisaria ser repetida. Além disso, a CTE melhora a legibilidade, especialmente em consultas com múltiplos níveis de agregação. Para consultas recursivas, a CTE é a única opção viável no SQL Server.

3.3.2 Funções de Janela (Window Functions)

As funções de janela realizam cálculos sobre um conjunto de linhas relacionadas à linha atual, sem colapsar o resultado em uma única linha (como fazem as funções de agregação tradicionais)[reference:5]. Isso é extremamente poderoso para rankings, totais acumulados e médias móveis.

Sintaxe geral:

Função() OVER (
    [PARTITION BY coluna]
    [ORDER BY coluna]
    [ROWS/RANGE BETWEEN ...]
)

Exemplo: Ranking de produtos por categoria

SELECT 
    p.Categoria,
    p.Nome AS Produto,
    p.Preco,
    ROW_NUMBER() OVER (PARTITION BY p.Categoria ORDER BY p.Preco DESC) AS Ranking,
    RANK() OVER (PARTITION BY p.Categoria ORDER BY p.Preco DESC) AS RankComEmpates,
    AVG(p.Preco) OVER (PARTITION BY p.Categoria) AS MediaCategoria
FROM Estoque.Produtos p
ORDER BY p.Categoria, Ranking;

Saída esperada (exemplo):

CategoriaProdutoPrecoRankingRankComEmpatesMediaCategoria
EletrônicosNotebook Pro8500.00115200.00
EletrônicosTablet X3200.00225200.00
EletrônicosFone BT3900.00325200.00
LivrosSQL Avançado180.0011120.00
LivrosPython Básico95.0022120.00

Observe que ROW_NUMBER sempre gera números únicos, enquanto RANK atribui o mesmo rank para valores empatados e pula posições. A coluna MediaCategoria calcula a média da categoria sem agrupar as linhas.

💡 Dica de performance Funções de janela geralmente são mais eficientes que self-joins ou subconsultas correlacionadas para cálculos analíticos. O otimizador do SQL Server consegue processá-las em uma única passagem pelos dados[reference:6].

3.4 Índices e Desempenho

3.4.1 O que são Índices?

Um índice é uma estrutura auxiliar que permite ao SQL Server localizar dados rapidamente, sem precisar varrer a tabela inteira (full table scan). Pense em um índice como o índice remissivo de um livro: em vez de ler todas as páginas para encontrar um tópico, você consulta o índice e vai direto à página correta[reference:7].

3.4.2 Tipos de Índices

  • Índice Clusterizado (Clustered): define a ordem física dos dados na tabela. Cada tabela pode ter apenas um índice clusterizado. Por padrão, a chave primária cria um índice clusterizado. Ideal para consultas de intervalo (range queries) e ordenação.
  • Índice Não Clusterizado (Nonclustered): estrutura separada que contém uma cópia das colunas-chave e um ponteiro para os dados reais. Uma tabela pode ter vários índices não clusterizados. Ideal para consultas de igualdade e junções.
  • Índice Filtrado (Filtered): índice não clusterizado com uma cláusula WHERE, indexando apenas um subconjunto de linhas. Útil para colunas com muitos valores NULL ou categorias específicas[reference:8].
  • Índice de Cobertura (Covering): índice não clusterizado que inclui todas as colunas necessárias para uma consulta, evitando acessos à tabela base (key lookup).

3.4.3 Criando Índices

-- Índice não clusterizado simples
CREATE NONCLUSTERED INDEX IX_Pedidos_DataPedido
ON Vendas.Pedidos (DataPedido);
GO

-- Índice composto (mais de uma coluna)
CREATE NONCLUSTERED INDEX IX_Pedidos_Cliente_Status
ON Vendas.Pedidos (ClienteID, Status);
GO

-- Índice de cobertura com INCLUDE
CREATE NONCLUSTERED INDEX IX_Pedidos_Data_Inclui
ON Vendas.Pedidos (DataPedido)
INCLUDE (ClienteID, ValorTotal, Status);
GO

-- Índice filtrado
CREATE NONCLUSTERED INDEX IX_Pedidos_Pendentes
ON Vendas.Pedidos (ClienteID)
WHERE Status = 'Pendente';
GO
⚠️ Cuidado com o excesso de índices Cada índice adicional ocupa espaço em disco e degrada o desempenho de INSERT, UPDATE e DELETE, pois o SQL Server precisa atualizar todos os índices afetados. A regra de ouro é: indexe o que é realmente consultado, mas não indexe tudo.

3.4.4 Fragmentação e Manutenção

Com o tempo, operações de inserção, atualização e exclusão podem fragmentar os índices, reduzindo a densidade das páginas e degradando o desempenho. Para diagnosticar:

SELECT 
    OBJECT_NAME(ips.object_id) AS Tabela,
    i.name AS Indice,
    ips.avg_fragmentation_in_percent,
    ips.page_count
FROM sys.dm_db_index_physical_stats(
    DB_ID(), NULL, NULL, NULL, 'LIMITED'
) ips
INNER JOIN sys.indexes i ON ips.object_id = i.object_id 
    AND ips.index_id = i.index_id
WHERE ips.avg_fragmentation_in_percent > 10
ORDER BY ips.avg_fragmentation_in_percent DESC;

Se a fragmentação estiver entre 10% e 30%, use ALTER INDEX ... REORGANIZE. Acima de 30%, use ALTER INDEX ... REBUILD[reference:9].

3.5 Normalização e Desnormalização

3.5.1 Normalização

A normalização é o processo de organizar dados em tabelas relacionadas para eliminar redundância e evitar anomalias de inserção, atualização e exclusão. As formas normais mais aplicadas são:

  • 1FN (Primeira Forma Normal): elimina grupos repetidos e atributos multivalorados. Cada célula contém um único valor atômico.
  • 2FN (Segunda Forma Normal): elimina dependências parciais. Todos os atributos não-chave dependem da chave primária completa.
  • 3FN (Terceira Forma Normal): elimina dependências transitivas. Atributos não-chave não dependem de outros atributos não-chave.
📐 Exemplo de violação da 3FN Considere uma tabela Pedidos com as colunas: PedidoID, ClienteID, NomeCliente, CidadeCliente. Aqui, NomeCliente e CidadeCliente dependem de ClienteID, não diretamente de PedidoID. Isso é uma dependência transitiva. A solução é separar os dados do cliente em uma tabela Clientes.

3.5.2 Desnormalização

A desnormalização é a introdução deliberada de redundância para melhorar o desempenho de leitura. É comum em data warehouses e sistemas analíticos, onde consultas complexas com muitos JOINs podem ser custosas[reference:10].

Exemplo: Em vez de sempre fazer JOIN entre Pedidos e Clientes para obter o nome do cliente, você pode armazenar NomeCliente diretamente na tabela Pedidos. Isso acelera relatórios, mas exige cuidado para manter a consistência (se o cliente mudar de nome, todos os pedidos precisam ser atualizados).

🧠 Pare e Pense #2

Pergunta: Em um sistema de e-commerce com milhões de pedidos e consultas frequentes de relatórios gerenciais, você normalizaria ou desnormalizaria? Justifique considerando o trade-off entre integridade e desempenho.

Reflexão: A resposta ideal é uma abordagem híbrida. Mantenha o modelo transacional (OLTP) normalizado para garantir integridade, e crie um data warehouse ou uma camada de agregação desnormalizada (OLAP) para relatórios. Assim, você tem o melhor dos dois mundos: consistência nas operações do dia a dia e desempenho nas análises.

Passo 4: Consulta com CTE e Window Function

Vamos criar um relatório que mostra, para cada cliente, o total gasto, a quantidade de pedidos e o ranking.

WITH ResumoCliente AS (
    SELECT 
        c.ClienteID,
        c.Nome,
        COUNT(p.PedidoID) AS QtdPedidos,
        SUM(p.ValorTotal) AS TotalGasto
    FROM Vendas.Clientes c
    LEFT JOIN Vendas.Pedidos p ON c.ClienteID = p.ClienteID
        AND p.Status = 'Entregue'
    GROUP BY c.ClienteID, c.Nome
)
SELECT 
    ClienteID,
    Nome,
    QtdPedidos,
    ISNULL(TotalGasto, 0) AS TotalGasto,
    RANK() OVER (ORDER BY ISNULL(TotalGasto, 0) DESC) AS Ranking
FROM ResumoCliente
ORDER BY Ranking;

6. Ferramentas para Modelagem Relacional no SQL Server

6.1 SQL Server Management Studio (SSMS)

O SSMS é a principal ferramenta de gerenciamento do SQL Server. Ele inclui o Visual Database Tools, um conjunto de designers visuais para trabalhar com estruturas de banco de dados[reference:11].

6.2 Database Diagram Designer

O Database Diagram Designer permite criar, visualizar e modificar diagramas ER diretamente no SSMS. Você pode:

  • Adicionar tabelas ao diagrama e visualizar seus relacionamentos.
  • Criar e modificar chaves primárias, estrangeiras e restrições.
  • Criar índices diretamente nas colunas.
  • Exportar o diagrama como imagem para documentação.

Como acessar: No Object Explorer, expanda o banco de dados → clique com o botão direito em Database Diagrams → New Database Diagram[reference:12].

⚠️ Nota O Database Diagram Designer exige que o banco tenha os objetos de suporte necessários. Se for a primeira vez, o SSMS perguntará se você deseja criá-los. Isso é normal e seguro[reference:13].

6.3 Table Designer

O Table Designer é usado para criar e modificar tabelas visualmente. Você pode definir colunas, tipos de dados, restrições, índices e relacionamentos sem escrever T-SQL. É útil para prototipagem rápida, mas em projetos profissionais, prefira scripts T-SQL versionados.

6.4 Ferramentas de Terceiros

Além das ferramentas nativas, existem opções de terceiros amplamente utilizadas:

  • dbForge Studio for SQL Server: ferramenta completa com designer de banco de dados, comparação de esquemas e geração de documentação.
  • Redgate SQL Toolbelt: conjunto de ferramentas para desenvolvimento, comparação e implantação de bancos de dados.
  • DrawSQL: ferramenta online para criação de diagramas ER, colaborativa e com exportação para SQL.

7. Glossário

Schema (Esquema)
Contêiner lógico que agrupa objetos de banco de dados dentro de um mesmo banco. No SQL Server, é independente do usuário.
CTE (Common Table Expression)
Expressão de tabela temporária nomeada que existe durante a execução de uma única instrução. Melhora a legibilidade de consultas complexas.
Window Function (Função de Janela)
Função que realiza cálculos sobre um conjunto de linhas relacionadas, sem colapsar o resultado. Exemplos: ROW_NUMBER, RANK, SUM OVER.
Índice Clusterizado
Índice que define a ordem física dos dados na tabela. Cada tabela pode ter apenas um.
Índice Não Clusterizado
Estrutura separada que contém cópias das colunas-chave e ponteiros para os dados reais.
Normalização
Processo de organizar dados em tabelas relacionadas para eliminar redundância e evitar anomalias.
Desnormalização
Introdução deliberada de redundância para melhorar o desempenho de leitura.
Fragmentação
Condição em que as páginas de um índice estão fora de ordem física, degradando o desempenho de leitura.
Database Diagram Designer
Ferramenta visual do SSMS para criar e modificar diagramas ER diretamente no banco de dados.

8. Conclusão e Resumo

Nesta aula, percorremos um caminho completo: da modelagem conceitual ER (vista na aula anterior) até a implementação física no SQL Server. Vimos que:

  • Schemas são fundamentais para organizar objetos e implementar segurança granular. Evite concentrar tudo em dbo.
  • Tabelas bem projetadas incluem restrições de integridade (PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK, DEFAULT) que previnem dados inconsistentes.
  • CTEs e Window Functions são ferramentas poderosas para consultas analíticas complexas, melhorando legibilidade e desempenho.
  • Índices aceleram consultas, mas exigem equilíbrio: muitos índices degradam operações de escrita.
  • Normalização garante integridade; desnormalização melhora desempenho de leitura. A escolha depende do contexto (OLTP vs. OLAP).
  • Ferramentas visuais (Database Diagram, Table Designer) facilitam a modelagem, mas scripts T-SQL versionados são preferíveis em projetos profissionais.

O domínio desses conceitos é essencial para qualquer profissional de ADS que deseje atuar com desenvolvimento back-end, análise de dados, administração de bancos ou arquitetura de dados.
